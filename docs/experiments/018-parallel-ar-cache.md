`scripts/partition_ar.py prepare` inventories a frozen complete N32 candidate snapshot on allocated CPU resources. It applies the existing parser, cleanup and 32-token span, caches by actual token IDs plus layer tag and full AR contract, and skips every first-computed inherited key. Remaining effective keys are assigned by SHA256 modulo the declared 2–4 worker count. Preparation requires the exact coordinator generation gate, homogeneous intended split, frozen cohort/fresh-capture hashes, every source cell identity and fresh activation hash, and full N32 coverage. Terminal journal hashes or a source-bound flat snapshot are verified. Test preparation requires both manifest and coordinator frozen-test authorization; a flag alone cannot unseal it. The immutable plan binds source hashes, checkpoint hashes, encoder/scorer code hashes, candidate provenance, inherited shard identities and every partition file. Original full-text variants retain separate provenance, even when they share one scoring input.

`encode --index I` runs the unchanged encoder at fixed batch size 128 into that worker's own output directory. Workers never write inherited caches or one another's shards. Independent batch composition can alter small floating-point scores; record actual batch execution metadata and share the same merged cache across all method arms. Resume uses the existing exclusive writer lock and atomic completed shard indexes. Empty partitions are valid, not missing data.

`merge` requires every worker's terminal prepared-input run and exact planned key coverage. It rejects changed contracts/keys, duplicate keys across writers, foreign partition keys, invalid tensor rows, missing partitions and changed inherited shard provenance. The resulting read-only catalog references original tensors without copying them. It preserves every inherited vector row unchanged and uses the prepared original-bullet provenance, not the workers' explicit-phrase usage metadata. Existing `RawVectorCache` can read the catalog's ordinary index layout; no changes to its source are needed.

Tests exercise deterministic partitioning, exact row/provenance preservation, duplicate/foreign coverage failures, missing workers/terminal records, tampered contracts/token IDs and out-of-range rows. They passed on the allocated CPU runtime. The real comparison below supplements these implementation tests; neither establishes global GPU numerical equivalence.

Forecast only: the observed production rate is approximately 98 effective vectors/second on one H200. One million new keys would take about 2.83 hours on one GPU, 1.42 hours on two or .71 hours on four, plus inventory, model loading, merge and scheduling overhead. Actual held-out new-key counts and throughput must be measured; cross-stage cache reuse can reduce work. Reserve resources only when this saves meaningful time.
